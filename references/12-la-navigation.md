Chapitre 11 — La Navigation

Une bonne navigation est invisible. Les utilisateurs savent toujours où ils sont, où ils peuvent aller et comment revenir.

⸻

Objectif

La navigation est le système qui permet à l’utilisateur de se déplacer dans l’application.

Une bonne navigation répond instantanément à trois questions :

* Où suis-je ?
* Où puis-je aller ?
* Comment revenir ?

Si l’utilisateur hésite sur l’une de ces questions, la navigation doit être améliorée.

⸻

Pourquoi la navigation est-elle essentielle ?

Les utilisateurs n’apprennent pas une application par cœur.

Ils explorent.

Une bonne navigation réduit leur charge cognitive en leur donnant des repères constants.

Elle agit comme une signalisation dans une ville : elle guide sans attirer l’attention.

⸻

Les principes fondamentaux

Une navigation efficace est :

* cohérente ;
* visible ;
* stable ;
* prévisible ;
* concise.

Les menus ne doivent pas changer d’une page à l’autre sans raison.

⸻

Les niveaux de navigation

Une application peut comporter plusieurs niveaux de navigation.

Navigation principale

Elle donne accès aux sections majeures.

Exemple :

Accueil
Produits
Tarifs
Blog
Contact

Elle doit rester identique sur toutes les pages.

⸻

Navigation secondaire

Elle concerne une section spécifique.

Exemple :

Dans “Produits” :

Tous
Nouveautés
Promotions
Accessoires

Elle change selon le contexte.

⸻

Navigation contextuelle

Elle apparaît uniquement lorsqu’elle est utile.

Exemple :

Modifier
Dupliquer
Supprimer

sur une fiche produit.

⸻

Le logo

Le logo est l’un des repères les plus puissants.

Dans la majorité des applications, il permet de revenir à la page d’accueil.

Ne modifie pas ce comportement sans raison.

⸻

Les menus

Un bon menu possède peu d’éléments.

Idéalement :

* entre 5 et 7 entrées principales.

Au-delà, l’utilisateur doit analyser davantage.

Si le nombre de rubriques augmente, envisage une meilleure organisation ou un méga-menu.

⸻

Les intitulés

Les libellés doivent utiliser le vocabulaire des utilisateurs.

Préfère :

* Commandes
* Factures
* Clients

à des termes internes comme :

* Gestion
* Administration
* Back Office

s’ils ne sont pas compris par le public visé.

⸻

L’ordre des éléments

Place les rubriques selon leur importance.

Exemple :

Tableau de bord
Projets
Clients
Factures
Paramètres

Les tâches les plus fréquentes apparaissent en premier.

⸻

Indiquer la page active

L’utilisateur doit toujours savoir où il se trouve.

La section active doit être visuellement différente :

* couleur ;
* fond ;
* barre latérale ;
* soulignement.

Le changement doit être visible sans être agressif.

⸻

Les fils d’Ariane (Breadcrumbs)

Les fils d’Ariane sont utiles lorsque la structure devient profonde.

Exemple :

Accueil
>
Produits
>
Ordinateurs
>
MacBook Air

Ils permettent de remonter facilement dans la hiérarchie.

Ils sont particulièrement utiles dans les applications métiers et les catalogues volumineux.

⸻

La recherche

Lorsque le volume de contenu est important, la recherche devient un moyen de navigation.

Une bonne recherche :

* accepte les fautes de frappe ;
* propose des suggestions ;
* affiche rapidement les résultats ;
* mémorise les recherches récentes si cela apporte de la valeur.

⸻

Les filtres

Les filtres ne remplacent pas la navigation.

Ils servent à réduire un ensemble de résultats.

Bonnes pratiques :

* filtres visibles ;
* possibilité de réinitialiser ;
* indication des filtres actifs ;
* nombre de résultats mis à jour rapidement.

⸻

Les onglets (Tabs)

Les onglets permettent de changer de vue sans quitter une page.

Exemple :

Profil
Sécurité
Notifications
Facturation

Évite un trop grand nombre d’onglets. Si leur quantité augmente fortement, une autre structure est souvent plus adaptée.

⸻

Les menus latéraux

Les menus latéraux sont particulièrement adaptés aux applications riches.

Ils permettent :

* une navigation persistante ;
* une bonne évolutivité ;
* l’ajout progressif de nouvelles sections.

Les catégories peuvent être regroupées pour améliorer la lisibilité.

⸻

Les menus déroulants

Un menu déroulant doit être réservé aux actions secondaires.

Évite de masquer les fonctionnalités principales derrière plusieurs niveaux de menus.

⸻

Les méga-menus

Ils sont adaptés aux sites contenant un grand nombre de catégories.

Ils doivent :

* être bien structurés ;
* présenter des groupes logiques ;
* éviter les listes interminables.

⸻

Navigation mobile

Sur mobile, l’espace est limité.

Les modèles les plus courants sont :

* barre de navigation inférieure (pour les actions principales) ;
* menu latéral (drawer) ;
* onglets.

Les actions essentielles doivent rester accessibles avec le pouce.

⸻

Les liens

Un lien doit être identifiable.

Il doit :

* utiliser un style cohérent ;
* indiquer clairement sa destination ;
* montrer son état au survol et au focus.

Évite les formulations vagues comme :

« Cliquez ici ».

Préfère :

« Voir les détails de la commande ».

⸻

Les retours arrière

L’utilisateur ne doit jamais craindre d’explorer.

Prévois toujours un moyen simple de revenir à l’étape précédente.

Dans les parcours complexes, il est utile de conserver le contexte (filtres, recherche, pagination) lors du retour.

⸻

Les erreurs fréquentes

❌ Menus différents selon les pages.

❌ Trop de niveaux de navigation.

❌ Libellés ambigus.

❌ Rubrique active non identifiable.

❌ Recherche absente sur un grand catalogue.

❌ Filtres cachés.

❌ Menu mobile difficile à utiliser.

❌ Plusieurs systèmes de navigation concurrents.

⸻

Cas pratique

Imaginons une application de gestion de projets.

Mauvaise navigation

* Menu principal de 15 entrées.
* Icônes sans texte.
* Rubriques qui changent selon la page.
* Aucune indication de la section active.
* Recherche cachée dans un sous-menu.

L’utilisateur perd rapidement ses repères.

Bonne navigation

* Menu principal limité aux fonctionnalités essentielles.
* Sections regroupées par domaine.
* Recherche toujours visible.
* Rubrique active clairement mise en évidence.
* Fil d’Ariane sur les écrans complexes.

L’utilisateur se déplace naturellement sans avoir besoin d’apprendre l’interface.

⸻

Checklist du chapitre

Avant de valider la navigation :

* ☐ L’utilisateur sait toujours où il se trouve.
* ☐ La navigation principale reste identique sur toutes les pages.
* ☐ Les intitulés utilisent un vocabulaire compréhensible.
* ☐ Les actions les plus fréquentes sont les plus accessibles.
* ☐ La section active est clairement visible.
* ☐ Les fils d’Ariane sont présents lorsque la profondeur le justifie.
* ☐ Une recherche est disponible sur les contenus volumineux.
* ☐ Les filtres sont faciles à utiliser et à réinitialiser.
* ☐ La navigation mobile est adaptée à une utilisation tactile.
* ☐ Le retour en arrière conserve le contexte de l’utilisateur.

⸻

Ce qu’il faut retenir

La navigation est la colonne vertébrale d’une interface.

Elle ne doit jamais surprendre l’utilisateur. Au contraire, elle doit exploiter les conventions qu’il connaît déjà afin qu’il puisse se concentrer sur ses objectifs plutôt que sur le fonctionnement de l’application.

Une navigation réussie est stable, cohérente et discrète. Les utilisateurs ne la remarquent presque pas… parce qu’elle fonctionne parfaitement.

⸻

Notes d’application

Nous y définirons leur anatomie, les règles de composition, la hiérarchie interne, les variantes, les interactions et les cas d’usage (produits, profils, tableaux de bord, statistiques, contenus éditoriaux), afin de construire des composants réutilisables et cohérents dans un Design System professionnel.Chapitre 12 — Les Cartes (Cards)

Les cartes permettent d’organiser l’information en unités simples, lisibles et réutilisables.

⸻

Objectif

Les cartes sont aujourd’hui l’un des composants les plus utilisés dans les interfaces modernes.

On les retrouve dans :

* les dashboards ;
* les e-commerces ;
* les CRM ;
* les applications SaaS ;
* les blogs ;
* les réseaux sociaux ;
* les applications mobiles.

Une carte bien conçue permet à l’utilisateur de comprendre rapidement une information et d’agir dessus.

⸻

Pourquoi utiliser des cartes ?

Une carte représente une seule entité.

Par exemple :

* un produit ;
* un utilisateur ;
* un projet ;
* une facture ;
* un article ;
* une tâche.

Une carte ne doit jamais représenter plusieurs objets différents.

⸻

Les principes fondamentaux

Une bonne carte est :

* autonome ;
* cohérente ;
* lisible ;
* réutilisable ;
* facilement comparable aux autres cartes.

⸻

Une carte = une information principale

Chaque carte possède une information dominante.

Exemple :

Carte Produit

→ Nom du produit

Carte Employé

→ Nom de l’employé

Carte Projet

→ Nom du projet

Tout le reste est secondaire.

⸻

Anatomie d’une carte

Une carte est généralement composée de :

┌─────────────────────────────┐
│ Image / Illustration         │
│                              │
│ Titre                        │
│ Description                  │
│                              │
│ Informations secondaires     │
│                              │
│ Action principale            │
└─────────────────────────────┘

Toutes les cartes d’une même famille doivent partager cette structure.

⸻

Le titre

Le titre est toujours l’information la plus visible.

Il doit être :

* court ;
* clair ;
* unique.

Exemple :

✔ MacBook Air M3

✔ Projet Apollo

✔ Jean Dupont

Évite les titres trop longs qui cassent la grille.

⸻

L’image

Toutes les cartes n’ont pas besoin d’image.

Ajoute une image uniquement lorsqu’elle apporte une information.

Exemples :

✔ Produit

✔ Profil

✔ Immobilier

En revanche, une facture ou une notification n’ont généralement pas besoin d’image.

⸻

La description

La description complète le titre.

Elle répond à la question :

Pourquoi cette carte est-elle importante ?

Elle doit rester courte.

Deux ou trois lignes suffisent dans la majorité des cas.

⸻

Les métadonnées

Les métadonnées apportent du contexte.

Exemple :

Projet

Créé le 12 juin
12 tâches
3 collaborateurs

Produit

En stock
Livraison gratuite
★★★★★

Les métadonnées doivent être discrètes.

⸻

Les actions

Une carte contient généralement :

* une action principale ;
* éventuellement des actions secondaires.

Exemple :

Modifier

Les autres actions :

Partager
Dupliquer
Archiver

peuvent être regroupées dans un menu.

⸻

Les espacements

Toutes les cartes utilisent les mêmes marges internes.

Exemple :

24 px
Titre
16 px
Description
24 px
Bouton

Le rythme vertical doit être constant.

⸻

Les dimensions

Les cartes similaires doivent avoir :

* la même largeur ;
* la même hauteur lorsque cela facilite la comparaison.

Dans une grille de produits, des cartes de hauteurs très différentes rendent la lecture plus difficile.

⸻

Les bordures

Les bordures servent à séparer les cartes.

Elles doivent rester discrètes.

Évite les contours épais qui attirent inutilement l’attention.

⸻

Les ombres

Les ombres créent une impression de profondeur.

Utilise-les avec modération.

Une légère ombre suffit généralement.

Les ombres très marquées donnent rapidement une impression datée.

⸻

Les coins

Le rayon des coins doit être identique dans tout le Design System.

Exemple :

Toutes les cartes utilisent :

* 8 px

ou

* 12 px

Pas un mélange de plusieurs valeurs.

⸻

Les états

Une carte interactive possède plusieurs états.

Normal

État par défaut.

⸻

Hover

La carte indique qu’elle est interactive.

Exemple :

* légère élévation ;
* légère ombre ;
* contour accentué.

⸻

Focus

Visible lors de la navigation clavier.

Le focus doit rester clairement identifiable.

⸻

Active

La carte répond immédiatement au clic.

⸻

Selected

Une carte sélectionnée doit être identifiable.

Exemple :

* contour coloré ;
* fond légèrement différent ;
* coche de validation.

⸻

Les cartes cliquables

Deux approches sont possibles :

Toute la carte est cliquable.

Approche adaptée :

* catalogue ;
* galerie ;
* tableau de bord.

⸻

Seul un bouton est cliquable.

Approche adaptée :

* formulaires ;
* tableaux ;
* interfaces complexes.

Évite de mélanger les deux sans distinction.

⸻

Les cartes de statistiques

Exemple :

Chiffre d'affaires
125 000 €
+12 %

La valeur principale domine.

L’évolution est secondaire.

Les explications sont discrètes.

⸻

Les cartes de profil

Structure classique :

Photo
Nom
Fonction
Entreprise
Actions

Le nom est toujours l’information principale.

⸻

Les cartes produit

Structure recommandée :

Image
Nom
Prix
Description courte
Évaluation
Ajouter au panier

Le prix doit être immédiatement visible.

⸻

Les cartes d’article

Structure :

Image
Titre
Résumé
Auteur
Date
Temps de lecture

Le titre attire d’abord le regard.

⸻

Les cartes de tableau de bord

Une carte de KPI contient généralement :

Titre
Valeur
Variation
Période

La valeur est l’élément dominant.

⸻

Les cartes vides

Lorsqu’aucune donnée n’est disponible :

Aucun projet
Créez votre premier projet.
[Créer]

Une carte vide doit toujours guider l’utilisateur.

⸻

Les erreurs fréquentes

❌ Trop d’informations.

❌ Plusieurs CTA principaux.

❌ Images inutiles.

❌ Espacements différents selon les cartes.

❌ Titres trop longs.

❌ Cartes de hauteurs incohérentes.

❌ Métadonnées plus visibles que le contenu principal.

❌ Ombres excessives.

⸻

Cas pratique

Imaginons une grille de projets.

Mauvaise conception

* certaines cartes mesurent 200 px de haut, d’autres 450 px ;
* les boutons changent de position ;
* les titres s’étalent sur cinq lignes ;
* les actions principales ne sont pas alignées.

Le balayage visuel devient difficile.

Bonne conception

Toutes les cartes :

* utilisent la même grille ;
* possèdent les mêmes marges internes ;
* présentent les informations dans le même ordre ;
* alignent leurs boutons au même niveau.

L’utilisateur compare les projets en quelques secondes.

⸻

Checklist du chapitre

Avant de publier une carte :

* ☐ La carte représente une seule entité.
* ☐ Le titre est immédiatement identifiable.
* ☐ Les informations suivent une hiérarchie claire.
* ☐ Les espacements sont constants.
* ☐ Les actions principales sont faciles à trouver.
* ☐ Les métadonnées restent secondaires.
* ☐ Les états Hover, Focus et Selected sont définis.
* ☐ Les cartes similaires possèdent les mêmes dimensions.
* ☐ Les images apportent une véritable valeur.
* ☐ Les cartes restent lisibles sur mobile.

⸻

Ce qu’il faut retenir

Une carte est une unité d’information.

Elle doit permettre à l’utilisateur de comprendre rapidement :

* de quoi il s’agit ;
* pourquoi c’est important ;
* ce qu’il peut faire ensuite.

Lorsqu’un Design System définit clairement les règles des cartes, toutes les interfaces gagnent en cohérence, en lisibilité et en facilité d’évolution.

⸻

Notes d’application

Nous y intégrerons également des recommandations pour améliorer la lisibilité et les performances sur les interfaces riches en données.Chapitre 13 — Les Tableaux (Data Tables)

Un tableau n’est pas seulement une liste de données. C’est un outil d’analyse et de décision.

⸻

Objectif

Les tableaux sont omniprésents dans les applications professionnelles :

* CRM
* ERP
* SaaS
* Comptabilité
* Gestion de projet
* RH
* Finance
* Administration

Un bon tableau permet de :

* retrouver une information rapidement ;
* comparer plusieurs éléments ;
* filtrer ;
* trier ;
* agir sur plusieurs lignes.

⸻

Le rôle d’un tableau

Un tableau répond principalement à trois besoins :

* consulter ;
* comparer ;
* agir.

Si le tableau ne remplit pas ces trois fonctions, il doit être repensé.

⸻

Quand utiliser un tableau ?

Utilise un tableau lorsque :

* plusieurs objets possèdent les mêmes attributs ;
* l’utilisateur doit comparer des données ;
* des actions sont réalisées sur plusieurs éléments.

Exemples :

✔ Liste des clients

✔ Commandes

✔ Factures

✔ Utilisateurs

✔ Produits

⸻

Évite les tableaux pour :

* raconter une histoire ;
* afficher un seul objet ;
* présenter du contenu éditorial.

Une carte est souvent plus adaptée dans ces cas.

⸻

Anatomie d’un tableau

Un tableau est composé de :

┌───────────────────────────────────────────────┐
│ Barre d'outils                                │
│                                               │
│ Recherche                                     │
│ Filtres                                       │
│ Actions                                       │
├───────────────────────────────────────────────┤
│ En-têtes                                      │
├───────────────────────────────────────────────┤
│ Lignes                                        │
│                                               │
│                                               │
├───────────────────────────────────────────────┤
│ Pagination                                    │
└───────────────────────────────────────────────┘

Chaque partie possède un rôle précis.

⸻

Les colonnes

Une colonne représente toujours un attribut.

Exemple :

| Nom | Email | Société | Statut | Dernière connexion |

Ne mélange jamais plusieurs informations dans une même colonne sans raison.

⸻

L’ordre des colonnes

Les colonnes doivent suivre un ordre logique.

Exemple :

Nom

↓

Entreprise

↓

Statut

↓

Date

↓

Actions

L’information importante apparaît en premier.

⸻

Les largeurs

Toutes les colonnes n’ont pas besoin de la même largeur.

Exemple :

Nom

→ Large

Date

→ Petite

ID

→ Très petite

Description

→ Flexible

Le contenu détermine la largeur.

⸻

Les alignements

Texte

→ Aligné à gauche.

Nombres

→ Alignés à droite.

Dates

→ Toujours alignées de manière cohérente.

Cela facilite énormément la comparaison.

⸻

Les en-têtes

Les en-têtes doivent être immédiatement identifiables.

Ils utilisent généralement :

* une graisse supérieure ;
* un fond légèrement différent ;
* une séparation visuelle.

Les intitulés doivent rester courts.

⸻

Les lignes

Une ligne représente un objet.

Toutes les lignes doivent avoir :

* la même hauteur ;
* les mêmes espacements ;
* le même comportement.

⸻

Les actions

Les actions peuvent apparaître :

Dans chaque ligne

Exemple :

Modifier

Supprimer

Voir

⸻

Dans un menu

Exemple :

⋮

Lorsque plusieurs actions existent, le menu améliore la lisibilité.

⸻

Les sélections

Lorsque plusieurs lignes peuvent être sélectionnées :

Utiliser une case à cocher.

Exemple :

☐ Client A
☐ Client B
☐ Client C

Une fois sélectionnées :

Afficher les actions de groupe.

⸻

Les tris

Toutes les colonnes importantes doivent être triables.

Le sens du tri doit être visible.

Exemple :

▲

Nom

ou

▼

Date

⸻

Les filtres

Les filtres permettent de réduire rapidement le nombre de résultats.

Ils doivent être :

* visibles ;
* faciles à supprimer ;
* mémorisés lorsque cela est pertinent.

⸻

La recherche

Une recherche est indispensable dès que le volume de données devient important.

Elle doit :

* être rapide ;
* tolérer les fautes ;
* rechercher dans plusieurs colonnes si cela est pertinent.

⸻

La pagination

Lorsque plusieurs centaines d’éléments existent :

Afficher une pagination.

Éviter de charger plusieurs milliers de lignes simultanément.

⸻

Le défilement

Si le tableau est très large :

Le défilement horizontal doit rester utilisable.

Les colonnes importantes peuvent rester figées.

Exemple :

Nom

reste visible.

Les autres colonnes défilent.

⸻

Les états

Un tableau possède plusieurs états.

⸻

Chargement

Afficher :

Skeleton

ou

Indicateur de chargement.

⸻

Vide

Aucun résultat.
Essayez de modifier vos filtres.

Ne jamais afficher une table vide sans explication.

⸻

Erreur

Expliquer :

Pourquoi les données ne sont pas disponibles.

Que faire ensuite.

⸻

Les couleurs

Utiliser la couleur avec parcimonie.

Exemple :

Vert

→ Succès

Rouge

→ Erreur

Orange

→ Avertissement

Le reste du tableau reste neutre.

⸻

Les lignes sélectionnées

Une ligne sélectionnée doit être clairement identifiable.

Exemple :

* fond légèrement coloré ;
* bordure ;
* case cochée.

⸻

Les tableaux responsives

Sur mobile :

Un tableau de 15 colonnes devient inutilisable.

Solutions :

* masquer certaines colonnes secondaires ;
* transformer les lignes en cartes ;
* proposer une vue simplifiée.

Ne cherche pas à reproduire exactement le desktop.

⸻

Les performances

Pour les grands volumes :

Utiliser :

* pagination ;
* chargement progressif ;
* virtualisation des lignes lorsque nécessaire.

Une interface rapide améliore directement l’expérience utilisateur.

⸻

Les erreurs fréquentes

❌ Trop de colonnes.

❌ Colonnes inutiles.

❌ Largeurs incohérentes.

❌ Aucun tri.

❌ Aucun filtre.

❌ Tableau illisible sur mobile.

❌ Actions dispersées.

❌ Aucune indication de chargement.

❌ États vides oubliés.

⸻

Cas pratique

Imaginons un CRM contenant 25 000 clients.

Mauvaise conception

* toutes les colonnes visibles ;
* aucune recherche ;
* pas de filtre ;
* pas de tri ;
* actions mélangées.

Retrouver un client prend plusieurs minutes.

Bonne conception

* recherche instantanée ;
* filtres par entreprise, statut et date ;
* tri sur les colonnes principales ;
* pagination ;
* actions regroupées dans un menu ;
* colonnes essentielles figées.

L’utilisateur retrouve un client en quelques secondes.

⸻

Checklist du chapitre

Avant de publier un tableau :

* ☐ Chaque colonne possède une fonction claire.
* ☐ Les informations importantes apparaissent en premier.
* ☐ Les nombres sont alignés à droite.
* ☐ Les textes sont alignés à gauche.
* ☐ Les en-têtes sont visibles.
* ☐ Le tri est disponible lorsque pertinent.
* ☐ Les filtres sont faciles à utiliser.
* ☐ Une recherche est proposée sur les grands ensembles.
* ☐ Les états Chargement, Vide et Erreur sont prévus.
* ☐ Le tableau reste utilisable sur mobile.

⸻

Ce qu’il faut retenir

Un tableau n’est pas un simple conteneur de données.

C’est un outil d’analyse.

Plus les utilisateurs trouvent rapidement l’information qu’ils recherchent, plus le tableau est efficace.

La simplicité, la cohérence et les performances sont plus importantes que la quantité d’informations affichées.

À partir du prochain chapitre, nous allons traiter les Dashboards, un sujet central pour les applications SaaS, les CRM et les outils métiers. Nous verrons comment organiser les KPI, les graphiques, les tableaux, les filtres et les cartes afin de créer des tableaux de bord qui facilitent la prise de décision. Ce chapitre intégrera des principes d’UX, de hiérarchie visuelle et de design de l’information pour concevoir des interfaces réellement orientées vers l’action.
